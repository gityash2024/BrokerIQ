# Immutable staging release workflow

Existing connected staging is brokeriq.mymultimeds.com / brokeriqapi.mymultimeds.com, API3100/web3101 and PostgreSQL5433 brokeriq_b2b_20261015. It contains Rahul's real business records and connected WhatsApp/Housing. No fixture/seed/reset acceptance here.

1. Finish checks and commit/push; pin one full commit. `ops/build-android-release.sh` refuses tracked modifications, clean-prebuilds Android, checks tracked screen/signing/SQLCipher configuration, assembles a release, verifies package/version/signing certificate and writes actual SHA256/bytes plus commit metadata under the ignored private releases directory. This is build evidence, not installed-device acceptance.
2. Transfer the APK and android-release.json over SSH to a new `/opt/brokeriq/artifacts/` directory. `ops/prepare-staging-candidate.sh COMMIT ARTIFACT_DIRECTORY` creates a fresh rc-COMMIT checkout, uses BrokerIQ's private Node22/Corepack and builds shared/API/web with bounded resources. It verifies artifact bytes/commit and generates release-manifest.json. It never changes active code, runs migrations/seeds, starts workers or reloads services.
3. Fresh consistent backup, encrypted off-host copy and actual scratch restore must pass before migrations. Preserve source/KYC/register evidence, active PM2/cwd/env checksums, unrelated service status and the current release for rollback. No backup is an unused build candidate.
4. Review and apply only additive migrations from the pinned candidate. All old clients must have a compatible error/update path, and the replacement APK must be available before enforcing a minimum version. Original public KYC references are retired only after separate original-preserving private migration and post-copy off-host restore proof.
5. Preflight candidate with jobs disabled and only bounded read-only smoke checks; do not expose a second live worker against the staging database. Switch the current symlink atomically and reload only brokeriq-api/brokeriq-web using the scoped ecosystem. If health, login or connected-account critical paths fail, switch back; do not reverse additive migrations or restore away new business rows.
6. Set actual publication timestamps in the candidate manifest at activation. Landing reads the manifest, separate portal/APK dates and real checksum; GET /release.json and API /health compiled identity expose the expected commit. APK app configuration embeds that same build commit/time. An absent/invalid production manifest fails explicitly instead of inventing a release timestamp.
7. Hash the full public APK download and compare with the signed local artifact. Check actual staging roles/screens, providers and the installed upgrade without uninstall. Capture UI screenshots from that release's controlled QA build, record provenance and publish their actual captured version; never label old images as the latest build.
8. Remove only enumerated unused build caches/archives/artifacts after comparing symlink, process cwd, nginx and downloadable references. Keep active release, one known rollback, actual backups/uploads/secrets/models. Record before/after bytes and unchanged unrelated services. A failed candidate is retained for diagnosis until explicitly identified as disposable.

The existing in-place bin/deploy.sh is not used for this release. Completing a staging update is not final production acceptance; the full original reconciliation ledger and open module/device/provider/manual/load gates still apply.
