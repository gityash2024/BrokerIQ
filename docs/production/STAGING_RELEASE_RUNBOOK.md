# Pinned staging publication

The connected staging contains real business records. Never seed it, run fixture suites against it, or start a second worker against its database.

1. Freeze and push the product commit. Run its real-PostgreSQL acceptance on a fresh isolated database. Record the exact commit, signed APK checksum, certificate, versionCode and native verification separately.
2. Retain an encrypted off-host backup chain and a successful actual scratch restore with table digests and media checksums. Preserve the active/rollback directories, uploads, settings, models and other projects. Keep at least20GiB usable server space.
3. `prepare-staging-source.sh FULL_COMMIT` may first compile shared/API while the signed Android build runs. It writes a pinned marker and releases the build lock. `prepare-staging-candidate.sh FULL_COMMIT ARTIFACT_DIRECTORY` verifies that marker, signed artifact and immediate accepted rollback APK before completing web/manifest. Neither phase seeds, migrates or starts jobs. Build the candidate in `/opt/brokeriq/releases/rc-<12-character-commit>` using private Node/pnpm and scoped environment files. Do not build inside the serving checkout. Verify all candidate identities and smoke it on private ports with background jobs disabled. Stop only those owned smoke PIDs after checking their working directories.
4. Before switching, run `ops/prepublish-staging-apk.cjs FULL_COMMIT APK_SHA256` on the server. This copies only the checked immutable APK into the currently serving downloads directory, never overwrites a different existing artifact, and checks the complete canonical HTTPS download. It does not update the old manifest, timestamps, PM2 or database. Next.js indexes public files at startup: if the copied APK returns404, refresh only `brokeriq-web` while it still serves the existing release, then rerun the full-download check. Do not switch merely because the file exists. Preserve the immediately previous accepted APK in the new candidate too.
5. Review the release-specific rollback configuration. Build42's protected rollback is Build41 plus `/opt/brokeriq/ops/rollback-ecosystem-build41.cjs`: it preserves private KYC/OTP and temporarily blocks follow-ups and unsafe legacy connector mutations. Never substitute its ordinary old API or reverse additive migrations.
6. Set publication timestamps in the candidate manifest at actual publication time. Atomically switch `current`, then reload **only** `brokeriq-api,brokeriq-web` with their scoped ecosystem. Do not reload/save every PM2 service. Record other services' PID/status/restart counters before and after.
7. Wait for the **expected pinned** identities, not merely mutually consistent identities. Run `ops/verify-active-staging-release.cjs FULL_COMMIT VERSION_CODE APK_SHA256`. It requires current symlink, origin/public API, origin/public manifest, PM2 executing paths and full public APK bytes to match the independently tested values. During handover all-old matching responses are NOT success. Retry bounded read-only checks; rollback through the reviewed wrapper if the expected release never becomes healthy.
8. Update runtime update-link/latest-version settings without altering OTP or minimum supported version accidentally. Observe landing in Chrome and capture its actual labels. Save manifest, restore proof and verification output as evidence. Do not relabel older screenshots. This operational checkpoint does not close device/provider/performance/product gates.

Build42 exposed a defect in the temporary activation probe: it accepted API/web/APK mutual consistency while all three still answered Build41 during process handover. Independent exact-commit and full-download checks subsequently passed for Build42. Use the tracked strict verifier above for every future switch. A first canonical request during handover also returned404; prepublication prevents advertising a new artifact before both workers can serve it.


## Build46 activation and recovery correction

PM2 online/reload success does not prove new executable paths. Use the reviewed `/opt/brokeriq/ops/start-pinned-processes.cjs /opt/brokeriq/ecosystem.config.js` after candidate/symlink checks; it recreates only brokeriq-api/web registrations with absolute scripts, retains Node22 and verifies cwd/script. Capture/compare unrelated processes before/after. Do not use startOrReload as acceptance, and do not assume PM2 CLI parses a .cjs file because Node require succeeds.

Keep activation, strict exact-pin/public-full-APK verification and runtime latest-version update sequential and fail-fast. Update version/link only after the awaited verification succeeds; on failure restore both release identity and effective runtime link before continuing. Build46's first failed attempt and correction are documented in STAGING_ACCEPTANCE.

Build46 adds nullable follow-up identities and SMS enum (43 total migrations). Old45 Prisma cannot read SMS. Incident rollback45 must use `/opt/brokeriq/ops/rollback-ecosystem-build45.cjs` through start-pinned-processes.cjs, with ops/rollback-api-build45-db43.cjs and BOTH immutable45/46 directories retained. Wrapper uses45 code + generated46 client, stops jobs and blocks follow-up create/lead assignment/bulk/assistant. It preserves data/private KYC/email OTP; never reverse migrations or remove the generated-client dependency directory. Resolve incident with a tested forward fix before resuming paused work. This containment smoke is separate from a complete functional incident drill.

The reusable activate-staging-release.sh now fail-closes when candidate/previous migration directory digests differ. It requires the candidate private-smoke PIDs and actual off-host restore proof, verifies public prepublished bytes, creates a pinned rollback object, switches only BrokerIQ processes through start-pinned-processes.cjs, then awaits strict active verification BEFORE update-active-release.cjs. It never migrates/seeds. Runtime update failure is explicit and must be resolved before acceptance. For a changed migration set use a reviewed release-specific rehearsal/compatibility recovery procedure; do not bypass the digest gate.

After refreshing an existing Next.js worker, PM2 online can precede the public-file index becoming reachable. The activation helper retries exact complete-APK prepublication verification at most20 times with2-second intervals. A pre-switch failure leaves the old current/runtime intact; inspect and retain the first rollback config/process baseline before any reviewed retry. Never delete evidence merely to force a retry.

The local/CI database setup helper now requires an explicit PostgreSQL URL with a BrokerIQ test database name before running migrations or seeding. Missing URLs and production-named databases are rejected before connection. A fresh isolated setup applied the migration set and real master seed successfully, then the full API suite passed 431 tests with 28 configuration-dependent skips. Broker-first-only cases require their separate run. No connected staging fixture was used.

## Isolated Linux Android build

When the workstation lacks the required8GiB, use the separate BrokerIQ-owned Linux toolchain under `/opt/brokeriq/build-tools`. `ops/prepare-linux-android-toolchain.sh` verifies the official vendor downloads, requires the owner's existing accepted SDK license files, and does not accept licenses automatically. It requires30GiB before installation and20GiB afterwards. No global Java/SDK package or service changes are made. The first setup completed with Temurin17.0.21+9, SDK36, NDK27.1.12297006 and CMake3.22.1.

Build only a detached candidate prepared by `prepare-staging-source.sh`; never run clean prebuild in `current`. Run the build as a resource-limited owned systemd unit with private `GRADLE_USER_HOME`, the explicit toolchain environment, a maximum of two workers, and no background application jobs. Pass the signing properties through a root-only `/run` directory, rewrite only its keystore path, and preserve the existing signing certificate. Do not put passwords in command arguments, logs, Git or persistent candidate files. Remove the temporary signing directory after the build on success or failure. Retain the verified signed APK and native verification report separately from regenerable outputs. CPU/memory limits and resource observations must be recorded with the release evidence.

Build53 preflight: fresh isolated PostgreSQL suite435 passed,28 configuration-dependent skips,58 suites passed/4 skipped. This is test evidence only; it does not indicate the release has been published or installed on a device.

The first Linux build used a separate Kotlin JVM inheriting the1.5GiB Gradle heap. Resource throttling became excessive during native compilation, so the owned unit was stopped; its `/run` signing directory was confirmed absent and the serving API remained on healthy Build52. The same pinned, already-clean generated project resumed with one Gradle worker and `-Pkotlin.compiler.execution.strategy=in-process`, using1.5GiB heap/640MiB metaspace within a3GiB unit. Future clean builds use these low-memory defaults; `BROKERIQ_ANDROID_WORKERS=2` is an explicit override. AGP was observed starting three Ninja compiler processes despite the CMake parallelism hint, so that hint must not be treated as a hard resource limit. The owned unit's memory ceiling is authoritative. After memory recovered, its CPU allowance was raised from one to1.5 of the server's two cores; unrelated services were not reconfigured. A resumed build still runs generated security assertions, source identity, signing-certificate, permission and packaged-byte checks. This operational recipe change does not modify the application pin or establish artifact/device acceptance by itself.
