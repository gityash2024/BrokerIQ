# Dashboard current ownership and unread semantics

Task/detail APIs had current-lead ownership guards, but Today’s Focus and the legacy/current dashboard metric queries only tested the task/visit's old assignedToId. A historical stale task/visit could reveal the reassigned Lead's name/phone and inflate an Agent's KPI. All three dashboard API paths now require both current task assignee and the current non-deleted Lead in the same firm. Deleted leads are excluded for administrators too. Requirement/inventory/source summary queries also retain the Agent's permitted record scope.

One shared Inbox channel predicate drives list queries, unread-stats and both dashboard snapshots. Housing-only WhatsApp filtering remains, including non-deleted same-firm leads; other channels preserve their existing admin/assigned-Agent visibility. SMS and Email now participate in unread snapshots alongside website chat and WhatsApp. Each response distinguishes unreadConversations (chats) and unreadMessages (sum of stored unread counts); existing unread-stats conversation fields remain compatible. Legacy dashboard components no longer add a fabricated24 to unread data or label it24-hour volume.

A new real PostgreSQL/HTTP scenario uses a stale follow-up/visit belonging to another agent's Lead, a deleted Lead, owned tasks, multiple unread messages per SMS/Email conversation, a non-Housing WhatsApp conversation and a read mutation. It verifies active/legacy dashboards and KPI boundaries, matching counter semantics and decrement on read. The first test used the wrong legacy response property name; corrected to actual todayFollowUps/todayVisits, then all19 permission/composer cases pass in Broker-first mode. Workspace types pass. Physical push/read/realtime, complete dashboard design/drilldown and all role/provider acceptance remain OPEN. Source follows Build46 and awaits the next pinned release.
