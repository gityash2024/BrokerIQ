# Concurrent first-save Inventory retries

An actual20-request PostgreSQL/HTTP probe found that the first keyed Inventory creation could return409 for identical concurrent retries. One record survived; the problem was false conflict responses, not duplicate committed inventory. The previous empty-update Prisma upsert included nested contacts and could race at the compound unique constraint before a later lookup observed the record.

Keyed creation now acquires a transaction-scoped advisory lock over firm plus client mutation ID before lookup. One create commits the record and contacts; other requests read the same authorized record. Creation audit is emitted once for the new record. A supplied outer transaction retains the same lock and atomicity without nesting transactions. Requests without an ID preserve their existing behavior. Existing keyed first-write-wins compatibility also remains: a changed retry body cannot overwrite the original property. This correction does not claim a new changed-payload conflict contract.

The real probe passed: all20 requests returned201 with one ID, one contact and one creation audit. An identical key used in a different firm created a separate, correctly assigned record. The full isolated API suite passed436 cases with30 skips (28 separate Broker-first cases and two opt-in load/soak cases); the separate Broker-first run passed all28 cases across four suites. Native115 source tests passed. API typecheck and scoped lint passed with zero errors/12 existing warnings.

The probe's initial cleanup ran only after assertions, causing dependent fixed-count cases to fail as well when the primary race was detected. Cleanup now runs in finally and is restricted to the test's two isolated firms/key. A single loopback listener avoids artificial Supertest listener warnings during the20-request probe. No connected staging fixture, migration or source record was changed. This source is after the pinned Build53 candidate and requires a later coordinated release; it is not shipped by Build53.
