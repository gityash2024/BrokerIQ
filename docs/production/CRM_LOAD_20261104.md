# Local CRM concurrency checkpoint — 4 November 2026

The opt-in `apps/api/test/crm-load.e2e-spec.ts` starts the actual Nest application on loopback with the isolated test PostgreSQL database. It creates20 distinct active device sessions (one firm Admin and19 Agents),400 owned leads and1,000 private inventory records. Twenty workers each run five sequential journeys: scoped lead list, inventory list, owned lead detail and durable follow-up creation. Each session also performs actual HTTP refresh. The100 created tasks are checked in the database. The Agent list payloads must retain current record ownership.

The first run expected201 from the refresh endpoint; its documented200 response correctly failed that harness assertion. The corrected run passed. Its measured p95 was48.11ms for200 list requests,30.36ms for100 details,37.88ms for100 task mutations and60.30ms for20 refreshes. The report explicitly identifies the isolated local environment and does not claim staging/provider/device acceptance. Application source is the Build53 pin; this new optional harness is a separate validation addition. API typecheck and scoped lint passed.

Enable with `RUN_CRM_LOAD=true`, an explicitly isolated BrokerIQ test `DATABASE_URL`, and the normal Jest command targeting `test/crm-load.e2e-spec.ts`. Production/staging fixtures are forbidden. `RUN_CRM_SOAK=true` additionally runs a real two-hour read/write cycle: twenty sessions every five seconds, task creation once a minute and refresh every ten minutes. This duration is not shortened or inferred from the quick load run. The started soak remains pending until its actual completion report and zero-error result are recorded.

These measurements cover API/database request handling, not browser rendering, constrained phone networks, model inference, provider callbacks, worker interruption or shared staging capacity. The full launch performance/recovery gate remains open.
